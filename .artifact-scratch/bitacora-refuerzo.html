Eficiencia de desempeño 1.4 → 1.6 / 2.0

consultar_gfw_con_cache lanzaba un intérprete de Python nuevo (subprocess.run, sin timeout) por cada consulta a GFW fuera de caché. Se eliminó ese subproceso completo.

  • server/app/gfw.py: sync_lambayeque ahora se importa en el mismo proceso del servidor (mismo patrón que ya usaba gfw_client.py) en vez de ejecutarse como script aparte. Se eliminó _ejecutar_script, SYNC_SCRIPT y PYTHON_BIN, que quedaron sin uso.
  • server/app/gfw_client.py y scripts/sync_lambayeque.py: se agregó una requests.Session() reutilizable en vez de abrir una conexión TCP/TLS nueva en cada llamada a la API de GFW.
  • server/app/routes/fuentes.py: el subproceso de analyze_news.py (fetch + Claude) ahora tiene un timeout de 10 minutos con kill() si se excede, para no dejar un proceso huérfano corriendo indefinidamente.

Fiabilidad 0.7 → 1.3 / 1.5

No existía ningún manejador para excepciones no previstas, y no había ni un test de la capa HTTP ni del frontend.

Manejo de errores

  • server/app/main.py: nuevo @app.exception_handler(Exception) que registra el traceback en el log del servidor y responde siempre {"error": "Error interno del servidor"} con 500, en vez de dejar pasar una respuesta sin el contrato que usa el resto de la API.

Cobertura de tests — backend (Python / pytest)

  • server/tests/test_main.py: autenticación, validación de entrada, control de rol (403) y el nuevo manejador de errores (500), incluyendo un caso que simula la BD caída.
  • server/tests/test_auth.py: bloqueo por intentos fallidos, que un usuario no bloquea a otro con la misma IP, y que un login exitoso limpia el contador.
  • server/tests/test_routers.py: embarcaciones, reportes, zonas (listar), sugerencias y fuentes — routers que antes no tenían ningún test.

Cobertura de tests — frontend (antes: ninguna)

Se instaló y configuró Vitest + jsdom + Testing Library desde cero (vite.config.ts, src/test-setup.ts, script npm test).

  • src/lib/session.test.ts, src/lib/api.test.ts, src/lib/csv.test.ts: lógica de sesión, el wrapper de fetch y la exportación de CSV.
  • src/components/ErrorBoundary.test.tsx: que un error de render muestre el mensaje de recuperación en vez de una pantalla en blanco.
  • src/features/zones/pages/ZonesPage.test.tsx y src/features/audit/pages/AuditLogPage.test.tsx: comportamiento según el rol del usuario.
Resultado 68 tests de backend (antes 38) y 23 de frontend (antes 0) — 91 en total, todos verdes.

Seguridad 1.0 → 2.1 / 2.5

El rol de cada usuario (administrador / supervisor / analista) ya existía en la base de datos y viajaba en el token de sesión, pero ningún endpoint lo verificaba, y ninguna acción quedaba registrada a nombre de quien la hizo.

Roles aplicados de verdad

  • server/app/auth_dep.py: nueva dependencia requiere_rol(*roles).
  • server/app/routes/zonas.py: crear y eliminar zonas críticas ahora exige rol administrador (antes cualquier sesión válida podía hacerlo).

Auditoría (nueva)

  • db/schema.sql: tabla auditoria (usuario, acción, entidad, detalle, fecha).
  • db/procedures.sql: sp_auditoria_registrar (interna — nunca otorgada a la API, solo la llaman las demás funciones desde adentro) queda registrada dentro de sp_incidentes_confirmar, sp_incidentes_descartar, sp_incidentes_registrar, sp_zonas_crear, sp_zonas_eliminar, sp_sugerencias_aprobar_vincular y sp_sugerencias_rechazar. Se agregó sp_auditoria_listar para consultarla.
  • db/roles.sql: firmas de GRANT actualizadas con el nuevo parámetro de usuario.
  • server/app/routes/auditoria.py (nuevo): GET /api/auditoria, solo administrador.
  • server/app/routes/incidentes.py y sugerencias.py: cada acción ahora reenvía el usuario del token a la función SQL correspondiente.

Pantalla de auditoría (frontend, nueva)

  • src/features/audit/: tabla con fecha, usuario, acción y entidad afectada.
  • src/App.tsx: ruta /auditoria protegida — redirige a quien no sea administrador.
  • src/components/layout/Sidebar.tsx: el link "Auditoría" solo aparece para administradores.
Verificado en vivo Contra la base de datos real de desarrollo: crear/eliminar una zona y registrar un incidente quedaron en /api/auditoria con el nombre del usuario correcto; un analista pidiendo esa ruta recibe 403; y sp_auditoria_registrar sigue sin poder invocarse directo desde la API (permiso denegado, como se esperaba).

Protección 1.0 → 1.9 / 2.5

  • server/app/routes/auth.py: bloqueo de 15 minutos por (IP, usuario) tras 5 intentos fallidos de login seguidos.
  • Corrección de un side-channel de timing en el mismo archivo: antes, si el usuario no existía, se saltaba bcrypt.checkpw por completo, así que un usuario inexistente respondía más rápido que uno real — eso permitía enumerar usuarios válidos sin acertar ninguna contraseña. Ahora bcrypt.checkpw corre siempre, contra un hash señuelo cuando el usuario no existe.
  • SECURITY.md (nuevo): riesgos evaluados (acceso no autorizado, fuerza bruta, operaciones sin permiso, filtración de credenciales de BD, errores no controlados) y las limitaciones aceptadas explícitamente, en vez de dejarlas implícitas.

Capacidad de interacción 1.4 → 1.8 / 2.5

Corrección sobre esta sesión La evaluación inicial decía que la accesibilidad era pobre ("aria- en 1 solo archivo"). Al revisar a fondo, esa búsqueda estaba mal hecha: los modales ya usan role="dialog", aria-modal, aria-labelledby y cierran con Escape, y los botones con ícono ya tienen aria-label o texto visible. No hizo falta ningún cambio ahí.

Lo que sí era un problema real, descubierto durante esta misma sesión: al restringir crear/eliminar zonas a administrador en el backend, ZonesPage.tsx — que sí existe y es visible para cualquier usuario logueado — seguía mostrando el formulario completo y el botón de eliminar a un analista, que solo se enteraba del bloqueo con un 403 después de llenar todo.

  • src/features/zones/pages/ZonesPage.tsx: el formulario de "Nueva zona" y el botón de eliminar ahora se ocultan para quien no sea administrador, con un mensaje explicando por qué.

Cómo se verificó

Cada cambio se corrió, no solo se escribió:

  • Suite completa de backend (pytest) y frontend (vitest) en verde después de cada bloque de cambios: 68 + 23 = 91 tests.
  • tsc -b --noEmit y npm run build limpios tras los cambios de frontend.
  • La migración de base de datos (tabla auditoria, funciones nuevas, grants) se aplicó contra el Postgres real de desarrollo, no solo se redactó.
  • Flujo completo probado por HTTP contra esa base real: crear zona → aparece en la auditoría con el nombre resuelto → eliminar zona → queda esa acción también → un analista pidiendo la auditoría recibe 403. Los datos de prueba se limpiaron después.

Pendientes / riesgos aceptados

Documentados explícitamente en SECURITY.md, no ocultos:

  • El bloqueo de intentos de login vive en memoria de un solo proceso — si el sistema alguna vez corre en varias instancias detrás de un balanceador, el límite efectivo se multiplicaría.
  • La auditoría no cubre POST /api/fuentes/analizar (el análisis de noticias con IA).
  • No hay rate limiting general de la API más allá del login.
  • Nada de esto reemplaza una demo en vivo: tiempos de respuesta reales y una prueba de usabilidad con un usuario real siguen siendo lo único que puede subir Eficiencia y Capacidad de interacción más allá de esta estimación.
